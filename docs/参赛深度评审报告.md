# 链易配参赛深度评审报告

> 评审范围：项目源码、主前端、后端路由与服务、数据模型、测试与运行文档，以及附件《2026 年湖南省大学生计算机程序设计竞赛校级选拔赛——应用开发类竞赛》设计文档。
>
> 证据口径：源码和本地运行结果为一级证据；设计文档中的实验表格若没有仓库内的原始数据、脚本、随机种子和复现实验命令，只记为“文档主张”，不视为已验证结果。

## 一、结论先行

链易配**适合参赛，但当前不适合按设计文档原样参赛**。

它最有价值的真实主线是：

> 面向地方产业链的企业供需撮合平台，把“找供应商”延伸为“看产能、看信用、促沟通”，并给政府端提供产业链缺口和风险处置视图。

项目的工程基础已经足够做出可演示作品：Flask + React 的多角色系统、企业匹配、报价/沟通、订单履约、政府预警、产业链图谱、管理审核和演示数据均有代码和页面支撑。但文档把许多可选模块、演示脚本、模拟接口和历史遗留能力统一包装成“完整工业级系统”，造成技术叙事超过当前可证明的实现。

参赛建议评分：

| 维度 | 当前判断 | 说明 |
|---|---:|---|
| 需求价值 | 8/10 | 中小企业找供应商、判断产能和信用，政府补链强链，问题真实 |
| 产品完整度 | 7/10 | 主流程可跑通，但合同、外部数据、微信等闭环仍有模拟/降级 |
| 技术亮点 | 7/10 | 九维规则评分、图谱、风险工作流有展示价值；深度模型证据不足 |
| 比赛叙事 | 5/10 | 模块太多，创新点堆叠，容易被追问“到底哪部分真正落地” |
| 证据可信度 | 4/10 | 文档实验数字缺乏仓库内可复现材料，存在绝对化安全和效果表述 |

## 二、源码确认的真实系统边界

当前运行数据库是 SQLite，数据量为 32 家企业、72 个产品、16 条供需、8 条交易；前端构建和 TypeScript 检查已通过，排除一个与当前环境不匹配的测试文件后，已有 79 项测试通过。

### 已形成主流程的能力

1. 企业登录、角色路由和管理员审核。
2. 企业画像、产品目录、企业名录和供需发布。
3. 基于产品、距离、产能、技术、历史合作、信用、绿色等维度的规则匹配。
4. 匹配反馈、询价会话、意向报价、收藏、名片交换和拼单。
5. 订单、履约状态、产能日历和经营看板。
6. 政府预警、预警派单/处置、产业链图谱、PageRank/社区分析和招商缺口。
7. 企业审核、数据授权配置、外部接口配置、审计日志和定时任务。

### 有代码但不应在答辩中直接称作“已完整落地”的能力

| 能力 | 源码事实 | 应如何表述 |
|---|---|---|
| XGBoost 精排 | 只有在生成 `ranking_model.pkl` 后才进入线上；当前仓库没有该文件，环境也没有 XGBoost | “支持离线训练后启用的精排增强” |
| HAN+BPR | 有训练实现和 3059 个企业的嵌入文件，但当前环境没有 PyTorch/PyG；当前数据库只有 32 家企业 | “具备离线图嵌入能力，演示环境降级” |
| FAISS | 代码只在保存阶段写入 index，没有线上 `index.search()` 调用 | “可持久化向量索引”，不能说“当前线上 FAISS 检索” |
| SentenceTransformer | 在线首次请求异步加载，当前环境没有 sentence-transformers，因此实际匹配中语义分为 0/加载中 | “可选语义匹配增强” |
| CLIP | 单独页面和服务存在，但依赖 torch/open_clip 未纳入当前 requirements，当前环境不可用 | 砍出主流程，作为后续扩展 |
| FedLab | 只是 `scripts/fedlab_demo.py` 独立演示脚本，不在平台主链路 | 只能作为研究展望，不作为平台核心能力 |
| 强化学习 | `update_rl_signal()` 当前函数体只有参数占位，没有训练、策略更新或 RL 表 | 删除“强化学习已实现”表述 |
| 区块链存证 | 合作签署时生成 SHA-256 后写入数据库字段，没有链、节点、共识、交易回执或外部账本 | 改称“协议摘要哈希/篡改检测” |
| 电子合同 | 默认 `provider='mock'`；第三方失败时本地生成合同 ID、模拟签署成功和模拟 PDF | 改称“电子合同接口适配与演示模拟” |
| 工商/电力/税务数据 | 未配置接口时返回随机或示例数据，并明确标记 `is_mock` | 演示中必须显式标注模拟数据 |
| Hermes/微信 | 本地路由和测试闭环有实现，但需要真实 Hermes、微信配置和回调；企业微信回调仍有 TODO | 作为可选演示彩蛋，不承担主流程成败 |

## 三、设计文档中需要纠正的关键点

### 1. 技术栈写错

附件第五章写的是 Flask 3.x、Vue3、Element Plus、ECharts；实际项目是 Flask 2.3.3、React 19、Vite、TypeScript、Tailwind，并且仍混有少量旧 Jinja 模板。答辩材料必须以源码为准，否则评委打开项目后会立刻发现不一致。

### 2. “六层/五阶段”叙事不一致

摘要部分称“六层递进匹配流程”，第四章 4.2 又明确列为五个阶段。建议统一为：

> 结构化召回 → 九维规则评分 → 可选模型精排 → 图/语义增强重排 → 可解释输出。

并在每一阶段旁边标明“必选、可选、离线”属性。

### 3. 线上主链路被写得过于完整

`matcher.py` 的九维规则评分是稳定主链路。XGBoost 在不存在模型文件时直接跳过；深度学习模式在语义和 GNN 不可用时会明确降级为规则分，并把 Top3 分数线性校准到 85–98 的展示区间。这个“信心指数”不是经过概率校准的置信度，不能与 Hit@5 或真实成交概率混用。

此外，当前 API 的 MiMo 调用是同步 `llm.invoke()`，不是文档宣称的“异步回调、用户零阻塞”。如果 MiMo 未配置，接口返回基础匹配降级结果；这对稳定性是优点，但不能拿“云端深度精排已实时运行”来答辩。

### 4. 指标没有当前仓库证据

附件写有 3059 家企业、7605 个产品、477 条查询、Hit@5 94.5%、Precision@5 76.7%、平均 59ms、200 名采购人消融实验、4200 次安全测试，以及验厂成本下降 80% 等结果。但仓库中没有对应的完整实验脚本、原始查询集、ground truth、随机种子、硬件记录、结果文件和统计置信区间；当前运行数据库也不是这些规模。

这些数字可以保留为“历史测试环境中的文档记录”，不能改写成“本次可复现结果”。比赛材料应换成：

> 在当前演示数据集上完成了功能验证；模型指标待补充可复现实验脚本和原始数据后再公开。

### 5. 安全结论过度

“零越权、零误操作”“接近绝对安全”不成立。五道校验即使相互独立，也不能简单把各层成功率相乘；真实系统还要考虑密钥泄露、代理配置、重放、会话、日志、权限模型和依赖漏洞。项目的 Hermes Bearer Token、IP 白名单、TTL、二次确认是合理防线，但最多应写成“在规定测试用例和次数内未发现越权”，不能外推为生产安全证明。

尤其是微信 OpenID 支持登录后手动提交绑定，企业微信 GET/POST 回调仍有 TODO；`.env` 中还开启了 `DISABLE_API_AUTH` 演示配置。公开演示前必须明确这是本地 Demo 设置，不得部署到公网。

## 四、实现不足与优先级

### P0：比赛前必须修正

1. **收缩主线**：只保留“企业需求 → 智能匹配 → 查看产能/信用 → 询价报价 → 订单履约 → 政府预警/招商”的一条闭环。
2. **改文档口径**：把已实现、可选、模拟、规划中四类能力分栏；删除所有无法复现的绝对数字和“首次、工业级、零风险”表述。
3. **统一演示数据**：将当前 32 家企业等数据规模写入演示说明；不要让旧的 3059 企业嵌入文件和 32 家 SQLite 数据同时出现在同一叙事中。
4. **修正匹配可信度**：禁止把 85–98 的线性展示值叫“置信度”；展示真实维度分、规则贡献和数据来源状态。
5. **修复产能评分口径**：当前实现用 `available / max(1, demand_quantity / 100)`，把库存/产能单位与需求量缩放混在一起。应统一单位后使用 `available / demand_quantity`，并补充边界测试。
6. **关闭公网危险配置**：比赛现场若通过局域网演示，应保留登录鉴权；生产配置必须关闭 `DISABLE_API_AUTH`，并限制 Hermes/微信回调入口。
7. **补齐项目入口说明**：当前 `README.md` 基本为空，比赛提交包至少应包含启动命令、演示账号、数据初始化、可选依赖和已知边界。

### P1：有时间应补强

1. 为匹配算法增加固定测试集、标注规则、训练/验证切分、随机种子和一键评测脚本。
2. 若保留 XGBoost，提交模型文件或训练命令，并把 `XGBClassifier(binary:logistic)` 改成真正按查询分组的 `XGBRanker(rank:ndcg/rank:pairwise)`，或明确称为成交分类精排。
3. 线上真正使用 FAISS，或删除“FAISS 毫秒检索”表述；否则保持 NumPy/数据库小规模降级即可。
4. 把外部数据的 `is_mock` 状态在 UI 上显著显示，并为每条信用/风险结论显示数据来源和更新时间。
5. 为信用分增加版本化规则、可解释分项、人工申诉和防反馈自强化偏差。当前“高信用 → 更高曝光 → 更多交易 → 更高信用”可能形成马太效应，不应直接宣传为“市场自动净化”。
6. 将电子合同、发票校验、区块链哈希从核心创新中降级为“接口适配/演示能力”，除非接入真实合规服务。

### P2：可以作为后续路线

CLIP 图文匹配、联邦学习、Hermes 微信自动处置、政策模拟、区域对比、真实工商/税务/电力接入、完整电子签约和生产级图数据库运维。

## 五、哪些功能可以直接砍掉

### 直接从比赛主版本中移除

- CLIP 图文匹配页面；当前依赖重、与核心采购闭环关系弱。
- FedLab 联邦学习脚本；目前不是应用内流程，容易被追问数据隔离、聚合、隐私攻击和效果。
- “区块链存证”命名；保留 SHA-256 摘要即可。
- 政策模拟器、区域对比、导出审批等设计文档功能；当前主前端没有完整闭环。
- 电子合同下载、发票验证等旧模板入口；若没有真实第三方服务，演示价值低且法律风险高。
- 过度复杂的“九维 + XGBoost + HAN + BPR + MiMo + Bandit”全家桶叙事；保留九维规则和一个可解释增强点即可。

### 不建议砍掉

- 企业画像、产品/供需发布、匹配结果卡片。
- 产能状态、信用分、匹配理由和数据来源标识。
- 询价/报价/订单履约主链路。
- 政府端产业链图谱、缺口分析、预警派单和处理闭环。
- 管理员企业审核、演示数据、审计日志。

## 六、竞品对照与差异化判断

| 竞品/类别 | 公开能力 | 链易配不能硬碰的地方 | 链易配可借鉴/差异化方向 |
|---|---|---|---|
| Alibaba.com | 全球供应商、沟通、生产监控/验货、物流与 Trade Assurance | 供应商规模、交易基础设施和服务成熟度 | 不做“大而全”，聚焦地方产业链和政府协同 |
| Xometry | AI 制造撮合、Instant Quoting、全球供应商网络、质量/交付追踪 | 报价自动化、制造工艺和真实订单规模 | 把“地方企业产能、信用、产业链缺口”做深 |
| SAP Ariba | source-to-pay、供应商管理、风险合规、合同/采购/发票、企业级治理 | 企业采购流程、合规、集成和成熟度 | 以轻量化地方产业治理和中小企业低门槛为特色 |
| 找钢/工业品垂直平台 | 垂直行业价格、供需和履约服务 | 行业深度、价格数据和履约网络 | 选择一个湖南重点产业做真实数据和真实场景闭环 |

因此，比赛中不要把链易配描述为“另一个 1688/Ariba”。建议定位为：

> 一个面向地方政府和产业园区的产业链协同操作台：用可解释匹配连接企业，用信用与产能降低采购决策成本，用图谱和预警帮助地方补链强链。

## 七、推荐的比赛演示流程

用一个“电机/控制器采购”故事完成 8–10 分钟演示：

1. 以采购企业登录，展示经营驾驶舱：需求、信用、风险和待办。
2. 输入自然语言需求，例如“需要 100 件整车控制器，优先距离近、信用高、产能充足的供应商”。
3. 展示候选列表和维度解释：产品、距离、产能、信用、绿色；明确哪些是演示数据。
4. 点开一家供应商，查看产能利用率、资质、历史交易和风险标签。
5. 发起匿名询价，供应商侧提交意向报价，采购侧比较报价。
6. 生成订单并更新履约状态，展示信用事件/履约记录回流。
7. 切换政府端，展示产业链图谱和缺口分析。
8. 点开红色预警，完成派单、处理、审核闭环；Hermes/微信只在真实配置可用时展示，否则演示站内处置。
9. 最后用一句话收束：平台不是替企业做最终采购决策，而是把“找得到、看得懂、敢合作、能监管”串成闭环。

## 八、建议答辩时主动承认的边界

- 当前演示环境使用 SQLite 和演示数据，MySQL/Neo4j/Redis/外部接口是可替换部署能力。
- 匹配主链路是可解释规则评分，深度模型是可选增强，避免把降级逻辑说成缺陷。
- 合同、外部工商/税务、电力、微信均需真实账号和合规接口；未配置时系统使用明确标记的模拟/降级服务。
- 目前最应该继续投入的是数据闭环和可复现实验，而不是继续堆叠更多模型名词。
