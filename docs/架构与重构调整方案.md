# 链易配架构与重构调整方案

版本：1.0
制定日期：2026-09-15
适用范围：当前 `/Users/fujimiyakaori/Documents/ChatGPT/lypdemo` 项目的产品边界、业务逻辑、数据模型、后端架构、前端信息架构和工程治理

## CAPABILITY

### 能力重述

链易配要成为一个面向地方产业园区、链主企业和中小制造企业的产业链协同平台：企业发布真实的采购/供货需求，系统基于产品能力、可用产能、地理、可信标签、历史履约和数据新鲜度筛选并排序供应商；双方完成询价、报价、订单和履约后，平台把可授权的结果回流到企业信用、价格指数和政府补链预警中。

这意味着平台的核心不是“展示很多 AI 模块”，而是让以下事实持续发生并可追溯：

> 找得到合适企业 → 看得懂为什么推荐 → 敢发起询价 → 能完成订单 → 结果能回流 → 政府能看到经过脱敏和授权的产业信号。

### 固定产品原则

1. **交易事实优先于模型推断。** 订单、报价、履约事件、认证和外部数据必须有来源、更新时间和责任主体；模型只能生成候选、解释或建议，不能把推断写成事实。
2. **企业数据默认私有。** 企业级产能、报价、订单和发票不默认对外公开；公开展示只能是授权字段或满足最小聚合人数后的统计结果。
3. **匹配必须可解释且可降级。** 无向量库、无图谱、无 LLM 或外部接口失败时，系统仍用结构化规则返回可用结果，并明确降级原因。
4. **推荐不能造成信用马太效应。** 信用分影响排序，但不能决定唯一曝光；新企业、数据不足企业和低曝光企业要保留探索机会。
5. **政府端看“区域态势和行动”，不看企业隐私明细。** 只有经授权或聚合后的数据进入政府看板；补链建议必须显示证据和置信依据，并支持人工确认。
6. **先做一个产业集群。** 首期选择一个产业和一个区域验证数据闭环，不同时做通用制造业、跨境交易、金融、物流和全量政务数据接入。

## CONSTRAINTS

### 必须保留的业务主线

以下能力是当前项目的核心竞争方向，不能在重构中删除：

- 企业、链主、园区/政府、平台运营四类角色及其权限隔离。
- 企业画像、产品能力目录、供需发布和企业名录。
- 供需匹配结果中的产品、距离、可用产能、可信标签、技术/资质、历史履约和数据新鲜度解释。
- 询价、报价、会话、收藏/关注、订单和履约状态回流。
- 区域产业链图谱、产业缺口、风险预警、预警派单和处置闭环。
- 数据授权、数据来源、数据新鲜度和操作审计。

### 明确降级、延期或删除的能力

| 动作 | 模块 | 调整理由 |
|---|---|---|
| 删除首期主线 | CLIP 图像找产品 | 依赖重，与采购成交闭环弱；先保留为插件接口，不占主导航 |
| 删除首期主线 | FedLab 联邦学习 | 当前只是独立演示脚本，不影响核心撮合；真实联邦训练还需要参与方、隐私攻击评估和持续训练数据 |
| 删除命名 | 区块链存证 | 单机 SHA-256 摘要不是区块链；改为“业务事件摘要/篡改检测”，以后如有真实账本需求再接外部服务 |
| 删除首期自研 | 电子合同、发票 OCR、物流轨迹 | 合同签署、税务验真和物流都属于高合规/高集成领域；首期只保留标准适配器与状态回流，不自称已完成真实闭环 |
| 暂停 | 强化学习/Bandit 在线改权 | 当前 `update_rl_signal()` 只是占位；先积累曝光、点击、联系、报价、订单和履约标签，再做离线评估和 A/B 测试 |
| 合并 | 企业端“风险/预警/消息” | 统一成“风险与待办”，减少多个入口重复展示同一事件 |
| 合并 | 收藏、企业名录、销售控制台 | 收藏是企业关系资产，名录是发现，销售控制台是待处理商机；前端可分视图，后端归到 `Partner Relationship` 领域 |
| 合并 | 合同、发票、物流独立页面 | 在订单履约详情中作为可插拔履约凭证，不做三个孤立系统 |
| 迁移 | 顶层 `app/services/*.py` 业务实现 | 顶层已有大量兼容转发文件；业务实现统一进入 `app/modules`，旧路径只保留一个版本周期的兼容导入 |
| 保留但改名 | “信用分” | 改为“可信履约分”或“合作可信度”，显示分项、来源、版本、更新时间和申诉入口，不能暗示政府信用认定 |
| 保留但限权 | 政府大屏 | 只允许看聚合、脱敏、已授权数据；大屏不成为原始企业数据导出入口 |

### 不可破坏的领域不变量

1. 只有审核通过、账户未停用、企业数据未过期的企业，才能进入公开匹配候选；被暂停、注销或明确拒绝接单的企业不得被推荐。
2. 供应商候选必须同时满足硬约束：产品/工艺能力、需求数量或可分批数量、交付时间窗口、区域/运输约束、必要资质。
3. 产能必须带 `as_of` 时间和口径。没有更新时间或超过有效期时，不能显示“产能充足”，只能显示“产能未知/需确认”。
4. 报价在指定有效期内才参与比较；撤回、过期、异常或未通过质量门禁的报价不得进入价格指数。
5. 订单状态只能按状态机流转；任何状态改变都写入不可变的订单事件，不允许只改一个字符串而丢失历史。
6. 只有完成订单或被双方确认的履约记录，才能影响可信履约分；点击、浏览和普通报价只能影响推荐反馈，不得直接增加信用分。
7. 政府指标必须附带统计时间范围、样本量、数据来源和最小聚合阈值。默认少于 5 家企业的聚合不展示；价格指数首期建议至少 5 条有效报价，关键品类最好达到 10 条再对外发布。
8. 所有模型输出保存模型版本、输入数据快照/特征版本、生成时间和降级原因，支持复盘“当时为什么这样推荐”。
9. 所有跨企业读写先通过授权和租户边界检查；前端隐藏按钮不等于权限控制。
10. 外部接口失败不能静默生成看似真实的数据。演示数据必须有 `is_mock=true`，生产路径必须返回数据不可用、旧数据或待人工确认状态。

## IMPLEMENTATION CONTRACT

### 一、目标架构：模块化单体 + 事件驱动边界

首期不拆成微服务，采用一个 Flask 部署单元、清晰领域模块、异步任务和事件表的架构：

```text
React SPA
  │  REST / SSE（统一 /api/v1）
  ▼
API 层（认证、校验、分页、幂等、错误格式）
  ▼
应用层（Command / Query / 权限 / 事务边界）
  ├─ Partner：企业、组织、画像、产品能力、资质
  ├─ Sourcing：供需、匹配、询价、报价、关注关系
  ├─ Commerce：订单、履约、质量、凭证和评价
  ├─ Trust：数据来源、质量门禁、可信履约分、授权
  ├─ Risk：产业链图谱、指标、预警、处置、招商任务
  ├─ Collaboration：会话、消息、通知、文件事件
  └─ Platform：租户、身份、审计、配置、外部连接器、任务
  ▼
基础设施适配层
  ├─ MySQL：业务事实和不可变事件（唯一事实源）
  ├─ Neo4j：产业链关系投影和图查询（可重建，不做业务事实源）
  ├─ Qdrant：企业/产品/需求向量索引（可重建）
  ├─ OpenSearch：企业、产品、报价、审计日志全文检索（可重建）
  ├─ Redis：缓存、限流、短期会话（可选，不保存唯一事实）
  └─ Worker：数据导入、索引、预警、通知、报表和模型任务
```

#### 为什么不马上做微服务

当前代码仍有 Flask 路由、历史 `app/services` 兼容层、JSON 拍平模型、模拟外部接口和主前端重定向共存。现在拆服务会放大数据一致性、鉴权、事件重试和部署问题。只有当某个模块出现明确独立扩缩容需求时再拆：

- `Search/Matching`：向量召回和排序耗时明显、需要独立 GPU/CPU 扩容。
- `Ingestion`：外部数据同步量和失败重试影响主 API。
- `Notification`：微信、短信、邮件和站内信的发送吞吐独立增长。
- `Risk Analytics`：图计算、批量预测和政府报表有独立调度需求。

### 三、数据模型重构

当前模型大量把资质、授权、专利、合作案例、信用事件、发票和履约数据放在 JSON 中，短期演示方便，长期会导致筛选、审计、去重和权限控制困难。改成“核心查询字段关系化 + 原始响应 JSON 留档”的模式。

#### 3.1 关系化核心表

| 领域 | 新表 | 关键字段/约束 |
|---|---|---|
| 组织 | `organizations`, `organization_members`, `organization_roles` | 企业/政府/园区隔离；成员角色独立于企业实体 |
| 企业 | `enterprises`, `enterprise_profiles`, `enterprise_status_history` | 基本身份与动态画像分离；经营状态有来源和生效时间 |
| 产品 | `products`, `product_capabilities`, `product_aliases`, `product_specs` | 产品标准名、别名、规格、工艺和所属企业可查询；保留 `external_payload` 原始数据 |
| 资质 | `qualifications`, `qualification_evidence`, `qualification_reviews` | 颁发方、证书号、有效期、审核人、证据文件和状态；证书号按颁发方+编号去重 |
| 供需 | `inquiries`, `inquiry_items`, `inquiry_constraints` | 一个询价可含多个产品/规格/交付窗口；数量、单位和币种明确 |
| 匹配 | `match_runs`, `match_candidates`, `match_explanations` | 保存算法版本、特征版本、候选阶段、维度分、数据来源和降级原因 |
| 报价 | `quotes`, `quote_items`, `quote_revisions` | 报价有效期、最小起订量、交付窗口、付款条件、撤回/过期状态；禁止覆盖历史版本 |
| 订单 | `orders`, `order_items`, `order_parties` | 产品使用 `product_id`；历史快照另存，避免产品改名破坏订单事实 |
| 履约 | `fulfillment_events`, `quality_records`, `delivery_documents`, `invoices` | 每个节点带发生时间、操作者、来源和凭证；发票验真状态与外部机构分离 |
| 信任 | `data_sources`, `data_snapshots`, `data_quality_results`, `data_authorizations` | 来源、授权范围、更新时间、质量结果、撤销时间可审计 |
| 评分 | `trust_score_versions`, `trust_score_events`, `trust_score_appeals` | 规则版本、分项贡献、证据和申诉；分数不可只存当前值 |
| 风险 | `chain_relations`, `risk_signals`, `alerts`, `alert_workflows` | 事实信号、模型推断、人工确认分表或分状态；预警处置为事件流 |
| 协作 | `conversations`, `conversation_participants`, `messages`, `notifications` | 会话与 `inquiry_id/order_id` 关联；通知发送状态可重试 |
| 平台 | `audit_events`, `outbox_events`, `idempotency_keys`, `connector_configs` | 支撑异步一致性、幂等、审计和外部连接器 |

#### 3.2 迁移策略

1. 第一步新增表，不删除旧 JSON 字段；用一次性脚本把 JSON 数据导入关系表并记录 `migration_source`。
2. 第二步所有新写入只写新表，同时通过兼容投影更新旧 JSON，保证旧模板和旧 API 仍可用。
3. 第三步前端和查询全部切到新表；对旧字段做双读但记录命中率。
4. 第四步稳定运行一个版本周期后，将旧 JSON 标为只读，再在正式迁移中删除或归档。
5. 每一步都有回滚脚本、行数对账、孤儿记录检查和权限回归测试；不得用 `db.create_all()` 代替版本化迁移。

特别要改正：`Transaction.product_name`、`Quote.product_name`、`Alert.product_name` 等仅用字符串关联产品的方式。新表必须使用稳定 ID，同时保留交易发生时的 `product_name_snapshot` 作为历史快照。

### 四、匹配业务重构

#### 4.1 标准匹配流水线

```text
需求解析
  → 硬约束校验
  → 关键词/结构化召回
  → Qdrant 语义召回
  → Neo4j 产业关系扩展（可选）
  → 规则精排
  → 可选学习排序
  → 数据质量和风险门禁
  → Top 3 + 替代候选 + 人工协同入口
```

#### 4.2 评分规则

首期只使用可解释精排，不使用“线性校准到 85—98”的展示分。建议把总分拆为 0—100 的业务分，并返回真实分项：

```text
总分 = 产品/工艺 30%
     + 交付与产能 20%
     + 履约可信 15%
     + 距离/物流 10%
     + 价格竞争力 10%
     + 技术/资质 10%
     + 绿色与区域政策 5%
```

权重只作为默认值，需求创建时可由采购方调整；调整后必须保存 `preference_snapshot`。硬约束不应被权重抵消，例如“无必要资质”“无法满足交期”不能靠高信用分排到前面。

每个候选必须返回：

- `match_score`：排序分，不是成交概率。
- `dimension_scores`：分项分数及计算口径。
- `evidence`：例如“产能数据更新于 2 小时前”“有 2 项有效资质”“过去 5 次订单准时率 96%”。
- `data_freshness`：每个关键字段的更新时间。
- `missing_data`：缺失字段和对结果的影响。
- `risk_flags`：经营异常、报价异常、产能过期或供应商集中等风险。
- `fallback_reason`：向量库、图谱、外部模型或数据源不可用时的明确说明。

#### 4.3 学习排序和强化学习的门槛

先把 `MatchFeedback` 重构为曝光级事件：`impression → view → contact → quote → order → fulfilled → repeat`，并保存位置、算法版本和候选集合。至少有一个产业集群的稳定正负样本、时间切分和人工标注后，先试 `XGBRanker` 或 LambdaMART；只有在线实验能证明增益且有防偏置机制后，才评估 Bandit。

负样本不能简单使用“没有交易过的企业”，因为没有交易可能是未曝光、未响应或被价格拒绝。需要区分 `not_shown`、`shown_no_action`、`contacted_no_quote`、`quoted_lost` 和 `fulfilled`。

### 五、订单与履约状态机

主状态建议如下：

```text
Inquiry:      draft → published → matching → closed / cancelled
Quote:        draft → submitted → revised → accepted / rejected / expired / withdrawn
Order:        draft → pending_acceptance → accepted → in_production
              → shipped → received → quality_pending → completed
              ↘ cancelled                    ↘ disputed → resolved / refunded
```

约束：

- 接受报价生成订单时保存报价版本、产品规格、数量、价格、交期和付款条件快照。
- 订单创建不等于履约完成；现有 `Transaction.status` 默认 `completed` 的语义必须取消。
- 每次状态变化写 `OrderEvent`，事件包含操作者、时间、来源、前后状态和证据。
- 产能占用在订单 `accepted` 后产生，取消或完成后释放/结算；不能只读企业的一个 `current_orders` 字段判断全部产能。
- 电子合同、发票、物流和质检都是履约凭证适配器；适配器不可用时显示“未接入/待上传”，不能模拟成已签署或已验真。

### 六、风险与政府端重构

风险系统按四层分开：

1. **数据事实：** 进口依赖比例、供应商数量、经营状态、履约率、产能更新时间。
2. **规则信号：** 达到阈值后产生风险信号，带规则版本、样本窗口和证据。
3. **模型研判：** 对影响范围、替代路径和趋势做辅助分析，标明模型和不确定性。
4. **人工处置：** 政府或园区确认、派单、处理、复核和关闭，形成 SLA。

政府首页只保留四个动作区：

- 区域产业态势：企业数、品类、供需、有效产能，全部带时间范围和样本量。
- 供应链风险：风险信号、证据、影响范围和替代候选。
- 补链任务：缺口 → 候选企业 → 联系/招商任务 → 进度。
- 处置闭环：预警 → 派单 → 处理记录 → 复核 → 关闭。

删除或隐藏无数据支撑的“预测性大屏装饰”。政府端的数据导出必须走授权、审批和审计；对外展示企业数、价格和产能时采用最小聚合阈值，必要时使用区间而不是精确值。

### 七、API 契约

统一为 `/api/v1`，所有写接口支持 `Idempotency-Key`，所有列表支持 `page`、`page_size`、`sort`、`updated_since`，错误格式统一：

```json
{
  "error": {
    "code": "CAPACITY_DATA_STALE",
    "message": "供应商产能数据已超过有效期",
    "details": {"last_updated_at": "2026-09-15T08:00:00Z"},
    "request_id": "..."
  }
}
```

核心接口：

| 方法 | 接口 | 说明 |
|---|---|---|
| POST | `/api/v1/inquiries` | 创建采购/供货需求，保存约束、交期和偏好快照 |
| POST | `/api/v1/match-runs` | 创建一次可追溯匹配运行，返回 `match_run_id` |
| GET | `/api/v1/match-runs/{id}/candidates` | 返回 Top 3、替代候选、维度分、证据、风险和新鲜度 |
| POST | `/api/v1/candidates/{id}/contact` | 记录联系事件并创建/关联会话 |
| POST | `/api/v1/inquiries/{id}/quotes` | 提交报价，需有效期、交期、数量和条件 |
| POST | `/api/v1/quotes/{id}/accept` | 幂等接受报价并生成订单 |
| GET | `/api/v1/orders/{id}` | 返回订单状态机、事件、凭证和待办 |
| POST | `/api/v1/orders/{id}/events` | 写入履约事件，按角色和前置状态校验 |
| POST | `/api/v1/data-authorizations` | 企业授权数据类型、字段、用途、范围和有效期 |
| GET | `/api/v1/risk-signals` | 按证据、严重度、区域和状态筛选风险信号 |
| POST | `/api/v1/risk-signals/{id}/workflow` | 政府/园区派单、处理、复核和关闭 |
| GET | `/api/v1/admin/audit-events` | 审计查询，不允许普通企业跨租户访问 |

旧 `/match`、`/demand`、`/orders` 和旧 Jinja 页面先作为适配层转发到新应用服务，并在响应头返回弃用提示；不再让旧路由直接调用深层 service。

### 八、前端信息架构调整

#### 企业端

将主导航收敛为：

1. **工作台**：待处理询价、报价、订单、风险和数据更新待办。
2. **找合作**：供需大厅、企业名录、匹配结果、地图和关注关系。
3. **采购与销售**：询价、报价池、会话和商机。
4. **订单履约**：订单、产能日历、履约凭证和评价。
5. **企业可信**：画像、资质、数据授权、可信履约分和申诉。
6. **设置**：通知、成员、接口和安全。

移出主导航但保留插件入口：CLIP、融资推荐、电子合同服务配置、微信高级配置。企业用户首先看到“下一步要做什么”，而不是九个算法能力卡片。

#### 政府/园区端

1. 区域态势
2. 风险与预警
3. 产业链与缺口
4. 补链任务
5. 认证与数据治理

大屏是 `/gov/screen` 的展示模式，不作为唯一工作入口；预警处置、证据查看和权限审计必须回到可操作页面。

#### 管理端

1. 企业审核与组织
2. 数据源与质量
3. 匹配规则与实验
4. 风险规则与处置 SLA
5. 接口、密钥与限流
6. 审计与运维

删除“规则配置里直接改变线上权重”的危险操作；改为版本化草稿 → 离线评估 → 小流量发布 → 观察 → 回滚。

## NON-GOALS

本轮架构调整明确不做以下事情：

- 不把链易配改造成通用 ERP；ERPNext、Odoo 或 Dolibarr 只作为订单/库存/制造连接器参照，首期只选一个做 PoC。
- 不建设自营物流、支付、电子签名、税务验真或供应链金融基础设施；这些通过适配器接入。
- 不让政府端成为企业经营数据的全量浏览器；政府只消费授权和聚合数据。
- 不为了展示 AI 而把 LLM、GNN、CLIP、联邦学习、RL 全部接入在线主链路。
- 不在没有标注数据和实验脚本的情况下承诺 Hit@K、转化率、延迟或成本下降数字。
- 不在当前边界未稳定前拆微服务、上复杂消息中间件或引入多个同类搜索数据库。

## REFACTOR BACKLOG

### P0：1—2 周，先建立可信基线

1. 补齐 `README.md`，写清启动方式、数据库、演示账号、数据规模、真实/模拟边界。
2. 将 `is_mock`、来源、更新时间、新鲜度和降级原因纳入统一 `DataEvidence` 结构，并在前端显示。
3. 修复订单默认 `completed`、产品字符串关联、产能口径和匹配“伪置信度”。
4. 禁止生产配置使用 `DISABLE_API_AUTH`；统一请求 ID、错误格式、角色/租户检查和审计事件。
5. 增加匹配固定测试集、订单状态机测试、权限矩阵测试和外部接口失败测试。

### P1：3—6 周，重构核心领域

1. 新建 `app/modules` 和 `/api/v1`，把 `app/applications` 按 Partner/Sourcing/Commerce/Trust/Risk/Collaboration/Platform 重新归类。
2. 建立 `outbox_events` 和 worker，把预警、索引、通知、信用重算从请求线程移出。
3. 将 JSON 中的授权、资质、专利、信用事件、订单履约和告警工作流迁移到关系表。
4. 把匹配重构为“硬约束 → 召回 → 精排 → 证据解释”，接入 Qdrant；OpenSearch 只承担全文和审计搜索。
5. 将报价、订单、履约改成不可变事件驱动的状态机。

### P2：7—12 周，完成一条真实业务闭环

1. 选择一个产业集群和一个链主/园区，接入真实产品、供应商、产能、询价和订单数据。
2. 接入 Great Expectations 做导入质量门禁，OpenMetadata 记录数据源、owner、血缘、新鲜度和指标定义。
3. 评估 Keycloak；如果现有登录暂时够用，先用 OIDC 预留接口，不要同时改掉所有认证。
4. 将现有聊天与业务事件关联；Rocket.Chat 只在文件、群组和审计需求明显时做 PoC。
5. 用 Grafana 监控接口延迟、任务失败、数据陈旧、模型降级、消息失败和预警 SLA。

### P3：12 周以后，基于证据扩展

1. 有足够订单/履约标签后再做学习排序和 Bandit。
2. 真实使用向量索引后再决定是否保留 CLIP 图片匹配。
3. 真实多方数据隔离需求出现后再评估联邦学习。
4. 当搜索/匹配/数据同步出现独立扩缩容需求时，再拆服务。

## 90 天验收标准

| 领域 | 验收条件 |
|---|---|
| 产品 | 一个产业集群至少跑通需求、匹配、联系、报价、订单、履约和评价回流；每步可追溯 |
| 匹配 | 每个候选有硬约束结果、分项分、数据证据、新鲜度和降级原因；不存在伪置信度 |
| 数据 | 企业、产品、产能、报价和风险的来源、更新时间、质量状态可查询；演示数据显式标识 |
| 订单 | 无法跳过状态机；订单事件可审计；产品、报价、交期和价格有历史快照 |
| 政府 | 只显示授权/聚合数据；每条预警可看到证据、规则版本、样本窗口和处置状态 |
| 安全 | 企业、政府、链主、管理员权限矩阵自动化验证；敏感读写有审计；生产关闭演示鉴权 |
| 运维 | 外部接口、worker、索引、通知和模型降级都有指标和告警；失败可重试且不重复写入 |
| 工程 | `pytest`、前端 lint/build、迁移演练和关键 Playwright 流程进入 CI；旧 API 兼容层有下线时间 |

## OPEN QUESTIONS

这些问题不阻塞架构开始，但在接入真实客户前必须由产品负责人确认：

1. 首个试点产业和地区是哪一个？它决定产品规格、行业词表、图谱关系和第一批数据源。
2. 谁是付费主体：政府/园区、链主，还是两者联合？这决定权限、SLA、部署和合同边界。
3. 产能的标准单位、更新频率和“可接急单”的定义是什么？不能让不同企业用不可比的 `capacity` 数值参与排序。
4. 企业公开展示的最小字段和政府可见字段分别是什么？哪些数据允许进入区域价格/产能指数？
5. 订单履约的第一数据源是平台录入、Excel、ERP/MES，还是链主人工确认？第一阶段建议选一个可控的真实来源。
6. 是否要求多租户隔离、国密、等保或本地化部署？这些会影响 Keycloak、审计、密钥和部署方案。
7. 是否允许平台保留报价、履约和信用事件作为长期数据资产？这需要在用户协议和数据授权设计里明确。
8. 产品匹配的“同义词/行业词表”由谁维护？LLM 只能辅助建议，不能直接把未经审核的词写入生产词典。

## HANDOFF

当前方案已经足够进入实现阶段，但应按以下顺序执行：

1. 先做 P0 事实基线和状态机修正。
2. 再做数据模型双写迁移和 `/api/v1` 模块化单体。
3. 然后做 Qdrant/OpenSearch/Great Expectations 的单点 PoC，并用一个产业集群真实数据验证。
4. 最后根据真实负载决定 Keycloak、Rocket.Chat、Grafana 和 ERP 连接器的集成深度。

推荐的下一条工程任务不是“再接一个模型”，而是建立一个可复现的 `matching-evaluation` 流程：固定需求集、候选集、人工相关性、数据快照、算法版本和 Top-K/响应率/联系率/报价率指标。完成这个基线后，任何架构或算法改动都能用同一套事实判断是否真的变好。
